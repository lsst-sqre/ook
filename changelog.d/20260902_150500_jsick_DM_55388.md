### New features

- New `/ook/intersphinx/sources` registry API naming the documentation sites Ook pulls Sphinx `objects.inv` inventories from. A registration is an inventory URL plus a human title (which surfaces as the `collection_title` of every link ingested from the site) and an `enabled` flag; `POST`, `GET` (single and list), `PATCH`, and `DELETE` are all supported, and `GET /ook/intersphinx/sources?enabled_only=true` narrows the listing to the sites the next ingest run will visit. The inventory URL is a registration's identity, so registering one that is already registered — or moving a registration onto another's URL — is a `409` rather than a second row, and an `http` URL is refused up front because the ingest path can only fetch over `https`. Each registration also reports when Ook last attempted to ingest it (`date_ingested`), how that attempt ended (`last_status`), and why it failed (`last_error`); those three are written by ingest runs and refused in a request body, so a registration cannot claim an outcome it never had. Writes are gated by the `exec:admin` scope at the Gafaelfawr ingress — not the `write:intersphinx` scope that warms the inventory cache — since registering a site commits Ook to serving links from it. A registration is published by a Crockford Base32 `id` — the same checksummed, hyphenated form the rest of Ook's API uses for resources and link checks — and that string is what addresses it in `self_url`, in the `Location` header, in the `{source_id}` path of the single-source routes, and in the `source_id` of every `POST /ook/ingest/intersphinx` result; a mistyped ID fails its checksum and comes back `422` rather than as a lookup that quietly misses.
- New intersphinx ingest pipeline that turns those registrations into documentation links. `ook ingest-intersphinx` — intended to run as a scheduled cron job — pulls every enabled source's `objects.inv` through the intersphinx inventory cache, parses it, derives each Python object's place in the dotted-name hierarchy, and replaces that site's links in one transaction per site, taken under a lock on that site's registration so that a scheduled sweep and a manual run overlapping on one site queue behind each other instead of each leaving a second copy of its links; entities no source documents any more, neither directly nor anywhere below them in the hierarchy, are pruned. Re-running is idempotent, whether the runs overlap or not, and a site deregistered while its inventory is being fetched is left deregistered rather than having its links written back. Ingest looks after the freshness of its own inventories rather than inheriting whatever the cache happens to hold: a sweep revalidates any source whose cached copy has aged past the cache's freshness TTL, and giving `POST /ook/ingest/intersphinx` a `source_url` revalidates that one source however fresh its copy is, so a manual run right after a site republishes parses what the site publishes now. There is therefore no ordering between the two CronJobs — `ook refresh-intersphinx` warms the client-facing inventory cache, and ingest revalidates what it parses. A site whose origin cannot be reached to revalidate a copy Ook already holds is not a failure: its links are rebuilt from that copy, and the run reports it as served stale — in the CLI's summary line and as `cache_status` on each result of the API trigger — so an operator can tell links that describe the site now from links that describe it as of Ook's last successful read. A site whose inventory cannot be fetched or parsed keeps the links from its last successful ingest, has the failure recorded as `last_status` and `last_error` on its registration, and does not stop the run — the command then exits nonzero once the run has finished, so the CronJob shows red for a site Ook has stopped refreshing. `POST /ook/ingest/intersphinx` triggers the same run on demand and reports each visited source's outcome in its body; giving it a `source_url` ingests that one registered source, whatever its `enabled` flag says, which is how a registration is tried out before being turned on. Like the registry, it requires the `exec:admin` scope at the ingress.
- New `python` link domain in the Links API, serving the documentation those ingested inventories describe. `GET /ook/links/domains/python` publishes the domain's URI templates in the same shape `GET /ook/links/domains/sdm` does, and `GET /ook/links/domains/python/objects/{name}` returns the documentation links for one Python object, addressed by the fully qualified name a Sphinx cross-reference targets (`lsst.afw.table.SourceCatalog`). Every link carries its site's registered title as `collection_title`, so a reader can tell which documentation a link leads into when several sites document the same object; an object's links are ordered by that title, with the URL breaking ties, so several sites' links read as a stable site-by-site list wherever they are served from. An object Ook knows but no site currently gives a page — a package held in place by the documented objects beneath it — answers with an empty list rather than a `404`, which is reserved for a name nothing in the domain answers to. `GET /ook/links/domains/python/objects` lists every object in the domain with its links, paginated with keyset cursors and an `X-Total-Count` header the same way the SDM collections are; a domain nothing has been ingested into is an empty collection rather than a `404`. `GET /ook/links/domains/python/objects/{name}/children` pages the same way through the objects one object directly contains — a module's classes and functions, a class's methods — so a client walks the hierarchy a level at a time instead of receiving a whole subtree flattened into one listing; an object that contains nothing answers with an empty page, and only a name the domain does not know is a `404`.
- New `GET /ook/links/domains` index, the entry point to the Links API: it names every link domain — `sdm` and `python` today — and carries each one's entity and collection URI templates, so a client discovers which domains exist and how to address the things in them from one request instead of hard-coding a path per domain. Each entry also carries a `self_url` to the domain's own info endpoint, which publishes exactly the templates the index does.
