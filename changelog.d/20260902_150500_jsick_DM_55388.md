### New features

- New `GET /ook/links/domains` index, the entry point to the Links API: it lists every link domain (`sdm` and `python` today) with its entity and collection URI templates and a `self_url` to the domain's own info endpoint, so a client discovers domains from one request instead of hard-coding a path per domain.

- New `python` link domain in the Links API, serving the documentation the ingested Sphinx inventories describe. `GET /ook/links/domains/python` publishes the domain's URI templates in the same shape as the SDM domain, and `GET /ook/links/domains/python/objects/{name}` returns the documentation links for one Python object by its fully qualified name (`lsst.afw.table.SourceCatalog`), ordered by site title; a name the domain does not know is a `404`. `GET /ook/links/domains/python/objects` lists every object with its links, and `GET /ook/links/domains/python/objects/{name}/children` lists the objects one object directly contains (a module's classes and functions, a class's methods); both paginate with keyset cursors and `X-Total-Count` like the SDM collections. Containment follows the dotted name: an object nests under its parent as long as some registered site documents that parent, whichever site that is. Every object in a listing reports the Sphinx role it was declared with as its `domain_type` (`class`, `method`, `function`, `module`, or whatever a site's extensions emit, such as autodoc-pydantic's `pydantic_model`), and both listings take a repeatable `domain_type` query parameter that keeps only objects with one of the given roles; the vocabulary is open, so an unknown role yields an empty page rather than a `422`. The single-object endpoint reports the same role in an `X-Ook-Entity-Domain-Type` response header, keeping the bare list-of-links body every single-entity Links endpoint returns. A name one inventory declares under two roles keeps the first; a name two sites declare under different roles reports the most recently ingested site's role, so it can change as sites are re-ingested.

- New `/ook/intersphinx/sources` registry API naming the documentation sites Ook pulls Sphinx `objects.inv` inventories from. A registration is an inventory URL (its identity, so a duplicate is a `409` and `http` is refused), a human title that becomes the `collection_title` of every link ingested from the site, and an `enabled` flag. It supports `POST`, `GET` (single and list, with `?enabled_only=true`), `PATCH`, and `DELETE`, and each registration reports its last ingest as `date_ingested`, `last_status`, and `last_error`, which are written by ingest runs and cannot be set through the API. Registrations are addressed by Crockford Base32 IDs like the rest of Ook's API. Writes require the `exec:admin` scope at the Gafaelfawr ingress.

- New intersphinx ingest pipeline that turns registered sources into documentation links. `ook ingest-intersphinx`, intended as a scheduled cron job, pulls every enabled source's `objects.inv` through the intersphinx inventory cache, parses it, derives each Python object's place in the dotted-name hierarchy, and replaces that site's links in one transaction per site; objects no site documents any more are pruned. Re-running is idempotent and overlapping runs are safe: a site whose inventory bytes are unchanged since its last successful ingest is reported as `unchanged` and its links are left in place, and a registration deleted or repointed while its inventory is in flight is not written back. Ingest revalidates any cached copy older than the cache's freshness TTL, so it does not depend on the `ook refresh-intersphinx` job; when an origin cannot be reached to revalidate, the links are rebuilt from the cached copy and the result is reported as served stale (`cache_status`). A site whose inventory cannot be fetched or parsed keeps the links from its last successful ingest, has the failure recorded on its registration, and does not stop the run; the command exits nonzero afterwards so the CronJob shows red. An object whose Sphinx role is not ASCII is skipped with a warning rather than failing its site. `POST /ook/ingest/intersphinx` (also `exec:admin`) triggers the same run on demand and reports each source's outcome; giving it a `source_url` ingests that one registered source regardless of its `enabled` flag and revalidates its inventory first, which is how a registration is tried out before being turned on.
