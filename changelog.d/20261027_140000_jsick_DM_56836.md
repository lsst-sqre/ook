### New features

- New guarded HTTP client for every fetch of a URL Ook did not choose itself, and the intersphinx inventory cache now uses it so every socket it opens connects to exactly the address its SSRF guard validated, closing a DNS-rebinding gap the cache has had since 0.25.0: a host could resolve to a public address for the guard's lookup and to an internal one for the connect. The requested URL, every redirect hop, and the refresh job's re-check of a stored URL are each pinned this way; the cache's error responses, negative caching, and ETag revalidation are unchanged. The client and its guard live in the new `ook.services.guardedhttp` package, which the cache and the link checker now share: `resolve_and_validate` refuses a host unless every address it resolves to is globally routable, and the client from `create_guarded_client` dials the validated address through a custom httpcore network backend, `PinningNetworkBackend`, while the request keeps its hostname, so TLS SNI, certificate verification, and connection reuse all stay keyed by hostname. A request that reaches the backend without a validated address fails closed: the backend guards the host itself, logs a warning, and refuses to connect to a non-public address. GitHub OIDC verification and Ook's other requests to URLs it chooses itself keep using the plain HTTP client. A link-check failure for a host that does not resolve now names the host in its error detail. `httpcore` is now a direct dependency, and `httpx` is bounded below 0.29 because the guarded transport builds on its internals.

- `ook linkcheck-recheck` gains repeatable `--include-status-code <code>` and `--include-status <broken|blocked|failing>` options that force a one-off recheck of the still-referenced URLs whose stored result matches any of them, even when they are not yet due. Run `ook linkcheck-recheck --include-status-code 421` once after deploying this release to re-verify the URLs stored with a 421, and `ook linkcheck-recheck --include-status blocked` to re-verify `blocked` rows that may have been the Cloudflare side of the same connection-reuse bug. A URL that is due anyway is enqueued once, an `unsupported` URL is never forced, and the completion log reports the number of forced rechecks. A forced recheck never lengthens a still-blocked URL's backoff: a `blocked` URL that comes back inconclusive again keeps its blocked count and next scheduled recheck, while a URL the forced recheck settles is updated exactly as a scheduled recheck would update it. With neither option, the command enqueues the same URLs as before. Forced URLs are published in recheck messages with a new `force` field, which tells the consumer to recheck them regardless of their schedule; messages without the field are handled as before.

### Bug fixes

- The link checker no longer reports a working page as an HTTP 421 (Misdirected Request), or as `blocked` behind a 403, because its host shares CDN addresses with another checked host, as docs.python.org and pypi.org do on Fastly. Since 0.23.0 the checker guarded against DNS rebinding by rewriting each request's URL host to the validated IP address, which keyed the HTTP client's connection pool by IP: a request for one hostname could reuse a keep-alive connection opened for another hostname at the same address, and the CDN refused it, with a 421 on Fastly or with a 403 on Cloudflare that the checker reported as `blocked`. The checker now fetches through the guarded HTTP client, which pins each socket to the validated address below the connection pool while the request keeps its hostname, so a connection is only ever reused for the hostname it was opened for.

- The link checker now treats an HTTP 421 (Misdirected Request) as inconclusive, like a 429 or a 503: the URL is reported `blocked` with the error `HTTP 421 (misdirected request)`, never `broken`, and the result neither advances nor resets the failing-to-broken ladder. A 421 means a CDN edge refused the connection the request arrived on, not that the link is broken, yet it previously counted as a failure and could escalate a working link to `broken`. A contributed result with status 421 is classified the same way, and Ook's own checks and contributions now share one set of transient status codes. Link-check failure details also include the `via` and `x-served-by` headers when the response carries them, so a failure served by a Fastly or other Varnish-based edge can be identified the way Cloudflare's `server`, `cf-mitigated`, and `cf-ray` headers already identify Cloudflare.
