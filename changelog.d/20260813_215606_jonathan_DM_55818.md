### Bug fixes

- Guarded intersphinx conditional revalidation against a redirect chain that has been re-pointed since the last fetch. A refresh replays the stored `ETag` and `Last-Modified`, but those validators were minted by the terminal of the *previous* chain, and an alias re-pointed at an older resource would answer a false `304` — leaving Ook serving the old version's bytes marked fresh while `resolved_url` (and the permanent-redirect header derived from it) named the new terminal, and, because the validators never changed, repeating the same false `304` on every subsequent run so it could never self-heal. Two changes close that: `If-Modified-Since` is now dropped as soon as a hop redirects, since a modification date is only meaningful against the resource it was read from (`If-None-Match` is kept — a strong validator stays trustworthy wherever the chain lands, and RFC 9110 §13.1.3 gives it precedence anyway); and a `304` whose observed terminal differs from the stored `resolved_url` is discarded as a validation of some other resource, with the whole chain re-walked unconditionally so the new content, terminal, and hop record all come from the same fetch. A `304` from an unmoved terminal still revalidates the stored copy in place, updating the resolved-chain columns from the chain that revalidation walked.
