### Bug fixes

- Guarded intersphinx conditional revalidation against a redirect chain that has been re-pointed since the last fetch. A refresh replays the stored `ETag` and `Last-Modified`, but those validators were minted by the terminal of the *previous* chain, and an alias re-pointed at an older resource would answer a false `304` — leaving Ook serving the old version's bytes marked fresh while `resolved_url` (and the permanent-redirect header derived from it) named the new terminal, and, because the validators never changed, repeating the same false `304` on every subsequent run so it could never self-heal. The stored validators are therefore sent only where they hold: to the terminal that minted them when the row records one, and — for a row that records none — along the chain but with `If-Modified-Since` dropped as soon as a hop redirects, since a modification date is only meaningful against the resource it was read from (`If-None-Match` is kept — a strong validator stays trustworthy wherever the chain lands, and RFC 9110 §13.1.3 gives it precedence anyway). A chain landing anywhere else is asked unconditionally and has to answer with the body, so the new content, terminal, and hop record all come from that one fetch. A `304` from the terminal that minted the validators still revalidates the stored copy in place, updating the resolved-chain columns from the chain that revalidation walked.
